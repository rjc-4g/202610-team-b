# 開発ルール

このプロジェクトの開発ルールを記載します。作業前にこのファイルと[ライブラリ利用ルール](dependencies.md)を確認してください。

## 開発の進め方

1. 対応する[Issue](https://github.com/rjc-4g/202610-team-b/issues)を確認する。
2. 対応するIssueの作業用ブランチを作成する。既存の作業用ブランチがある場合は切り替えて使う。
3. 実装後に`cargo run --locked`、`cargo test --locked`、フォーマット・静的解析の確認を実施する。
4. 作業記録を更新し、変更をローカルにcommitする。通常の開発作業はここまでとし、pushは行わない。
5. ユーザーから明示的に指示された場合にのみ、pushやPull Requestの作成を行う。PR本文に対象Issue、変更点、確認結果、未確認事項を記載する。
6. 管理・レビュー担当が差分と動作を確認し、指摘への対応後にマージする。

Issueごとの実装経緯・検証結果・レビュー事項は`docs/issues/`に記録します。
ドキュメント一覧と格納方針は[docs/README.md](README.md)を参照してください。

### コメントの記載方針

Rust初級者がコードを読みながら理解できるよう、日本語のコメントを手厚く記載します。

- 関数・構造体の役割、引数・戻り値、処理の流れ、実装理由を説明する。
- `async` / `.await`、所有権・借用、マクロ、エラー処理など、初級者に分かりにくい構文は使用箇所で意味を補足する。
- APIでは、URL・HTTPメソッド・呼び出される関数の対応や、応答が返るまでの流れも説明する。
- コードを変更したときはコメントも見直し、実装との食い違いを残さない。

### 定数の管理方針

- 値の意味を名前で明確にできる、複数箇所で共用できる、変更箇所を集約できるなど、定数化の効果がある場合は、定数用ファイル`src/constants.rs`に型付きの`const`として定義し、利用側から参照する。
- 定数名は`SERVER_PORT`のように意味が分かる大文字のスネークケースとし、用途・単位を日本語のコメントで説明する。
- 定数用ファイルは対象の定数を導入する際に作成する。すべての数値・文字列を機械的に定数化せず、実測値など実行時に変わる値は対象外とする。
- テストの期待値は、実装側の定数と共用することで誤変更を検出できなくならないようにする。

## ライブラリ・ツールチェーン

依存ライブラリやツールチェーンの導入・更新の承認、初回取得、バージョン固定、Cargoの実行方法は[ライブラリ利用ルール](dependencies.md)に従います。

## ドキュメントの管理

- 開発ルールの追加・変更は、このファイルと必要に応じて`dependencies.md`へ反映する。
- ルートの`README.md`には、プロジェクト概要、利用方法、起動・停止・テスト手順とドキュメントへのリンクを記載し、開発ルールの本文は記載しない。
- AI向けの`AGENTS.md`は、`docs/`配下の開発ルールへの参照を記載する。
